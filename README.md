# 多平台会话数据中台 × Agent 标签数据引擎

> 新加坡某 AI 语音创业公司 · AI 产品经理 · 2026.01 – 2026.08
> 把散落在多平台的销售对话，变成统一的会话资产，再自动加工成模型训练数据

---

## 一、项目背景

业务是面向跨境市场的 AI 驱动销售：管理大量 Telegram / WhatsApp 等平台账号，覆盖多语言市场。当时已有一个**群聊营销引擎**解决了群聊自动化，但它直接对接平台连接层，暴露出三个问题：

1. **会话散落** — 业务员要在多个平台间切换，没有统一入口
2. **语言断层** — 客户用葡语 / 泰语 / 英语，业务员用中文，缺乏双向翻译
3. **资产流失** — 对话数据没有统一沉淀，无法回放复盘，更无法导出为训练语料

第三点是最贵的损失。销售对话天然带有「真人如何赢单」的知识，也天然带有成交结果这一**弱监督信号**——不沉淀下来，等于每天都在丢弃免费的训练数据。

## 二、我的角色与职责

负责该中台的产品方案设计、架构框架定义与技术选型课题拆解，并设计其上层的 Agent 标签数据引擎方案。

### 1. 会话数据中台（下层）

把平台连接、消息存储、翻译、分析抽出来做成通用基础设施，让群聊营销引擎降级为「众多消费方之一」。

- **Connector 抽象** — 定义多平台连接器的统一注册与事件格式，平台能力差异通过 `CapabilityManifest` 声明
- **统一数据模型** — 账号、外部身份、会话、参与者、消息、附件、原始事件、分析结果、翻译记录、匿名别名共 10 张核心表
- **消息双链路** — 入站（原始事件 → 归一化 → 语言识别 → 翻译 → 分析 → 事件分发）与出站（草稿 → AI 优化 → 翻译 → 发送 → 回写）
- **翻译层** — 入站 / 出站双向翻译、语言识别、原文译文双轨保留、术语表

### 2. Agent 标签数据引擎（上层）

把中台沉淀的真实对话，自动加工成可直接喂给训练的带标签数据集。

- **标签体系** — 意图 / 阶段 / 策略 / 情绪 / 合规五个回合级维度 + 结果一个会话级维度，MVP 只取 `intent + stage + 采纳 + outcome`
- **三层标注漏斗** — 规则预标 → LLM 打标（带置信度）→ 人工抽检（低置信 + 抽样 + 关键样本）
- **结果回标** — 用成交结果做弱监督，只从赢单会话学风格，用赢 / 输的相似回合构造偏好对
- **训练映射** — 一条对话同时产出 SFT 正样本、DPO 偏好对、蒸馏 CoT 素材

### 3. 两层之间的契约

系统只通过一个接口耦合——中台的 **Agent Facade**（标准事件 + 命令），也就是引擎层的**数据入口契约**。

## 三、关键设计取舍

- **为什么把中台做成独立产品，而不是群聊引擎的扩展** — 群聊只是消费场景之一，后面还有私聊客服、客户运营。做成扩展，第二个消费方接入时就得推倒重来
- **为什么原始事件必须从第一天开始存** — 解析逻辑可以重写、分析模型可以升级，但当时收到的原始 payload 丢了就永远丢了。这条在项目早期最容易被省掉，也最贵
- **为什么原文和译文必须双轨保留** — 回放要还原语境、复盘要核对翻译误差、训练导出要选择原文或对齐语料；分析层只吃译文会让情绪和行业术语被误读，而这恰恰是标签体系里最需要准确的维度
- **为什么出站链路要留存草稿态** — 业务员的每一次「采纳 / 改写 / 拒绝」本身就是一次高质量的人类偏好标注，是零成本的 DPO 数据源。链路设计时就要把它当数据资产，而不只是一次发送动作
- **为什么成交结果只能当粗粒度奖励** — 成交是会话级的，摊到每句话就是错误归因；而且头部业务员赢单可能是因为线索好而非话术好，不加控制会学成假因果
- **为什么数据按「租户 × 语言」分桶且绝不跨租户混训** — 合规与质量双重要求；每桶训一个 LoRA 共享同一基座，天然同时实现私有化与多语言

## 四、成果

- 产出中台与数据引擎的完整架构方案，明确两层职责边界与唯一耦合契约
- 定义 10 张核心表的数据模型与双向消息链路
- 设计六维标签体系、三层标注流水线与结果回标机制，形成「对话 → 标注 → 训练 → 评测 → 灰度 → 回流」的自进化闭环
- 拆解 8 项必答技术选型课题（技术栈、开源框架评估、存储、实时推送、翻译选型、客户端方案、Connector 抽象、部署架构）作为工程侧研究输入
